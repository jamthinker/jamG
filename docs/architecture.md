# Architecture and delivery plan

## Decisions

Java 21, Maven modules `core`, `server`, `client`, and `cli`. The first milestone uses no runtime dependencies: a synchronized access-ordered map, JDK HTTP server, and JDK HTTP client. HTTP makes functional testing straightforward; it is not a claim that this transport is optimal for high throughput. Binary keys use URL-safe Base64 in paths, values use raw HTTP bodies. JSON control responses use a small fixed schema. No Java object deserialization.

The embedded core has linearizable operations within one cache in one JVM. A single lock gives precise compare-and-set, TTL, and eviction behavior. It trades throughput under contention for a small, auditable implementation. TTL uses absolute wall-clock deadlines; clock jumps affect expiration. Versions increase within one cache instance, including after clear. They are not durable identifiers yet. Reads copy values; caller mutation cannot change cached data.

The cache uses LRU and accounts for `128 + key.length + value.length` bytes per entry. This is an estimate, not a hard heap limit: collection overhead, transient copies, HTTP buffers, and JVM memory are additional. Oversize entries fail before mutating state. Expired entries are removed on access and every second. Capacity is per cache; the server limits cache count. Total estimated cache budget is capacity times maximum caches. No external services are required.

Initial targets, to measure rather than assume: server JAR below 5 MiB, idle heap below 32 MiB, startup below two seconds, and fewer than 30 JVM threads on a documented local test machine. Do not interpret these as benchmark results or SLAs.

## Milestones and acceptance gates

1. In-memory embedded cache, headless server, client and CLI. Validate TTL, LRU, atomic creation/CAS, binary data, bounded values, named cache isolation, concurrency and CLI exit codes over real loopback HTTP.
2. Durable recoverable cache. Select append-only CRC-protected WAL, `FileChannel.force(true)` before write acknowledgment by default, checkpoint + atomic manifest replacement, versioned format, directory locking, snapshot backup, offline restore and compaction. Eviction must be a durable deletion so evicted values cannot resurrect. Refuse service after uncertain disk writes; never silently fall back to volatile mode. Test forced termination, torn tail recovery (only incomplete final records), interior checksum corruption (fail closed), disk full, TTL and versions across restart, and concurrent checkpoint/write races. An async durability option must explicitly permit losing acknowledged writes. This is a proposed design; persistence is not in milestone 1.
3. Distribution. Evaluate Apache Ratis against size, memory and operational goals before committing. Proposed default: majority-committed, per-partition linearizable operations with leader reads or ReadIndex, stable virtual partitions, replicas distributed across nodes, topology epochs and fenced ownership. Minority partitions reject operations; timeouts may leave write outcome unknown. Persist idempotency request IDs in the replicated state machine for retryable writes. No cross-partition transaction claim. Membership and ownership changes must be committed, not inferred independently from heartbeat timeouts. Use joint-consensus membership changes and snapshot transfer. Start with one consensus group if group-per-partition costs exceed the lightweight budget. Test partitions, leader replacement, stale owners, restart and rebalancing before claiming failover. No hand-built consensus. Clustering is not implemented in milestone 1.
4. Remote deployment: TLS/mTLS, read/write/admin authorization, bounded ingress with overload responses, connection and header/body timeouts, audit events without cached values, metrics, systemd/container packaging and reproducible benchmarks. Remote binds are rejected until this gate passes.

Single-node atomicity is not distributed consistency. The current server cannot be safely deployed remotely, used for durability, or presented as production-ready. No process recovery, replication, discovery, topology routing, online backups or failover are provided by milestone 1. Later milestones remain explicit work rather than placeholder commands that appear to succeed.
